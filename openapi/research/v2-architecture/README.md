# V2 architecture investigation and implementation plan

V2 is a useful independent test of the codegen refactor and a promising way to avoid v1's cross-resource compilation dependencies. It does not remove those dependencies from applications that still use v1. The experiment should first make a v2-only consumer independent of v1 Shared, then evaluate ordinary concrete v2 models with simple, changeable placement. Package boundaries remain experimental. Compare compiler inputs, binary/library artifact sizes, and LLVM IR using the current benchmark approach; repeated timing runs are outside the plan. Opaque v1 representations are a separate experiment.

This is a planning checkpoint on `expt/codegen-v2`, based on `5c0dafda38b01f022d1076c76cee4272f8f2dc5c`. There are no generator, runtime, manifest, feature, or generated-SDK changes. Breaking public changes are acceptable, but the initial experiment should keep the legacy output comparison available so unrelated changes cannot explain its results.

The two questions governing the work are:

1. Which existing refactor boundaries let v2 be added locally, and which remaining changes would make future schema, representation, or packaging changes simpler?
2. Can v2's actual relationships support small independently compiled resource families without lazy or opaque model fields, including when v1 and v2 coexist?

**Evidence and limits.** [inputs.json](inputs.json) records exact source revisions, channels, API revisions, URLs, and SHA-256 hashes. Both combined GA files exist at the existing `v2494` tag, commit `3e5f190f81ef54900d83909fc733226b87afccb1`, API revision `2026-08-26.dahlia`. The SDK file supplies resource, operation, and event annotations absent from the public file. The production input and fixtures remain unchanged. [schema-inventory.json](schema-inventory.json) and [inventory.py](inventory.py) record reproducible raw-schema observations. [baseline-shape.json](baseline-shape.json) identifies archived concrete-baseline measurements and their backup provenance. These are different measurement layers; none establishes a v2 compile-time speedup.

| Observation at the pinned GA revision | Implication |
| --- | --- |
| 23 v2 paths, 32 operations: 12 GET, 18 POST, 2 DELETE; all declared successes are JSON status 200 | No new HTTP verb or generalized success-status framework is needed for this input. JSON bodies and v2 pagination are needed. |
| 181 v2-prefixed SDK schemas, including 11 resource schemas, 22 event schemas, a generic error envelope, 146 detailed errors, and a deleted-object response | Do not equate schema count with public resource count or emit every error as an independently enabled family. |
| Zero structural references between v2-prefixed model schemas, or across the v1/v2 boundary, in both combined variants | At this revision there is no schema-reference requirement to co-locate v2 resource models with v1 or one another. Operation returns still introduce dependencies, such as Event Destination ping returning Event. |
| No expansion annotations, oneOf/anyOf/allOf nodes, or discriminators in those v2 model schemas | Concrete models are the appropriate initial representation. This finding is scoped to this pin and channel, not future or preview v2. |
| Account response: 215 object nodes with properties, 627 property entries, 200 enum nodes, 1,373 enum entries | Account is internally substantial even without external references. A blanket v2 Core package would make this relevant to small event consumers unless gated or split. |
| Event Destination response: 6 object nodes with properties, 30 property entries, 7 enum nodes, 19 enum entries | A useful small first resource. Its dependency slice should stay small. |
| Account create/update bodies contain 397/410 property entries before deduplication | Request code and repeated inline structures also need measurement. Removing cross-resource edges does not remove this work. |

Shape counts include inline occurrences and constant `object` enums, before Rust lowering and deduplication. They exclude annotations and examples. They are not canonical item counts, model-module SCC counts, or compiler source counts. The raw model-reference graph has isolated v2 nodes; the eventual emitted graph also needs IDs, helpers, requests, methods, reexports, and feature activation.

Operation error responses do contain unions: for example, Account creation lists 94 error-schema branches and Event Destination creation lists 5, in both combined variants. Those errors have scalar envelope fields rather than resource DTO references. Generic transport errors should preserve code/message and response information without forcing every operation's error union into all consumers. Typed error conveniences, if wanted, can be scoped to the resource integration. Zero unions in the named v2 model schemas is not a claim that every v2 response is non-polymorphic.

The combined SDK preserves the legacy input's 386 v1 paths at this pin, but only 1,600 of the cached legacy input's 1,735 schema values compare equal. That comparison is diagnostic, not an API compatibility judgment. Switching the normal input requires its own output comparison; the experiment can use an explicit input and scope first.

**How v1 and v2 should coexist.** Preserve qualified schema origins, operation paths, and object discriminator values. Keep `account` and `v2.core.account` as distinct model identities, regardless of their Rust display names. A public path such as `stripe::v2::core::Account` can be independent of physical crate ownership; it does not commit us to one `v2-core` crate. The existing item identities and canonical references are sufficient starting points. Namespaced facade paths need layout/rendering support, not a second identity system or cross-version deduplication.

Business interoperability is real. Stripe documents accessing Accounts through either version's endpoints, with the endpoint selecting the returned representation. Customer-configured Accounts can be passed to v1 requests through `customer_account`. An explicitly shared lightweight `AccountId` in the foundational types layer is reasonable for this documented identity. A common prefix alone is insufficient evidence to share any other ID or model. A v2 default payment method can remain an ID; it need not become a v1 `PaymentMethod` field. Do not invent typed model relationships absent from the schema merely to provide navigation conveniences. [Stripe migration guide](https://docs.stripe.com/connect/accounts-v2/migrate-integration)

API namespace, dated API revision, event format, and related-resource namespace are separate facts. This input includes two thin event types named `v1.billing.*`. Event Destinations also has a `snapshot`/`thin` payload choice. A thin notification can identify a resource without containing its DTO. The generic notification/event layer should remain independent of resource model crates. Typed resource-fetch helpers belong with the selected resource integration, or in a leaf adapter if necessary; putting all of them in a universal event crate would recreate model dependencies. Methods returning types in another crate do not require their models to share a crate, although they do introduce a compilation dependency. [Stripe event formats](https://docs.stripe.com/events/how-events-work)

**The existing runtime is the first compilation obstacle.** Both `async-stripe` and `async-stripe-client-core` unconditionally depend on generated Shared. Client configuration imports `AccountId`, `ApplicationId`, `ApiVersion`, and the default version from it. Transport errors use `ApiErrors`, whose concrete fields reference PaymentIntent, PaymentMethod, SetupIntent, and PaymentSource. Removing only the generated v2-to-Shared edge would leave this dependency intact. See [client-core exports](../../../async-stripe-client-core/src/lib.rs), [configuration](../../../async-stripe-client-core/src/config.rs), [transport](../../../async-stripe/src/hyper/client.rs), and [ApiErrors](../../../generated/async-stripe-shared/src/api_errors.rs).

The experiment needs a client path with no v1 DTO dependency. Reuse the existing foundational `async-stripe-types` crate for small shared primitives where appropriate; do not create another generic infrastructure crate by default. Separate API revision/header data from the enum extracted from v1 webhook creation. Gate the existing rich v1 error integration behind v1 support, retaining its behavior when enabled. A clean end state could expose a model-independent wire error envelope and optional typed v1 detail conversion, but changing v1 error ergonomics is not required to establish the v2-only boundary.

The baseline's physical Shared has 1,046 model components and 1,049 compiler source files in the archived all-features verification. Its largest represented model SCC has 98 modules, 230 canonical declarations, 1,270 struct fields, and 1,161 explicit enum variants. This difference is not a proof that the other components can all be split profitably. It does show that the current Shared placement is broader than a single unavoidable Rust cycle: it promotes cross-crate consumers' dependencies into Shared and propagates that choice. Ordinary one-direction dependencies are permitted between crates. [Placement algorithm](../../src/crate_inference.rs)

**Feature policy and organization candidates.** Existing domain resource features gate requests; model modules and Shared remain unconditional. A feature called `v2` layered onto that policy would offer little source isolation. Cargo features are additive and unified for a package, so v1 and v2 support must work together rather than select mutually exclusive versions of a client or type. [Cargo feature semantics](https://doc.rust-lang.org/cargo/reference/features.html)

Use resource-family choices for availability, transport choices for execution, and serde integration for trait support. Keep these axes distinct. If a `v2-events` option is needed, it should enable its concrete models and requests together; serde forwarding must not activate unrelated optional model packages. Logical families do not require separate published packages or flags at the outset. Generate dependency activation from actual type uses when necessary rather than maintaining a second hand-authored closure table. Do not add one flag per schema or operation. Existing `serialize`/`deserialize` compatibility flags can remain during the experiment; merging them into one serde integration flag is a separate ergonomic choice if the split has no demonstrated value.

| Candidate | Benefits | Cost or question |
| --- | --- | --- |
| One v2 package, with family gates on models and requests | Small packaging change; good control for comparing compiler inputs | Selected families share one compiler unit; feature combinations need checking |
| Packages matching Stripe `v2.core`, `v2.billing`, `v2.commerce` | Familiar grouping and a few compiler units | Core combines large Accounts with small event management; internal family gates may still be necessary |
| A few family packages: v2 Accounts, Events, Billing, Catalog | Heavy Accounts can compile independently of small Events; public namespace remains familiar | More manifests/releases; shared IDs and event conveniences require deliberate ownership |

Start with the smallest layout the slice needs; one experimental v2 package with clear module groups is a reasonable initial arrangement. Keep placement in a small explicit configuration or policy that can be changed without rewriting model inference, request semantics, or public paths. The table is a list of options for later experiments, not a required three-layout implementation or a preferred published package split. Avoid adding a general layout framework before an actual alternative needs it. Keep related account/person/token operations grouped logically, and keep all event-destination operations with generic Event and deletion responses. Keep truly common primitives small; never make a new global v2 Shared the default home for every multiply referenced type.

From a clean slate, the dependency direction would be: foundational types; model-independent client-core; transport/client plus optional facade dependencies on selected API families; independently owned family models and requests; optional webhook/resource adapters at the leaves. V1 families can continue to use their existing Shared while its representation experiment proceeds independently. A mixed application then pays for the v1 it actually selects, while a v2-only application can avoid it entirely. Breaking changes should be used to simplify ownership and availability, not to rename every public item before useful comparisons exist.

**Most valuable remaining refactor steps, in priority order.**

1. Complete the operation semantics carried from inference into `RequestModel`: full namespaced target, selected body media type, query parameters, selected success schema/status, and pagination kind. The renderer should print those decisions, and both transports should execute them. This removes the current scattered `/v1` stripping/prepending and POST-implies-form assumptions. Preserve namespace in selectors too. Keep this a small contract, not a general HTTP framework. [Request inference](../../src/requests.rs), [request model](../../src/request_model.rs), [request renderer](../../src/templates/requests.rs)
2. Make runtime primitives, configuration, and basic error handling independent of generated business models. This is required for useful v2-only compilation even though the schema graph is already separate. Preserve old v1 support through explicit optional integration while comparing the experiment.
3. Let final item/crate placement follow canonical represented uses after rewrites and lowering. Today component layout is frozen before those stages, and the later represented graph can validate the result but does not choose a different layout. Keep component ownership as a grouping hint; use `ItemLayout` for physical placement. SCCs constrain what can be separated, while acyclic dependencies are allowed. Reuse `visit_type_uses` and the existing module graph, including constructor signatures, IDs, and facades. Do not introduce a cached parallel graph or generic optimization engine.
4. Describe public namespace and family availability independently of file paths and stored representations. Use a simple family-to-items/dependencies mapping until actual cross-family requirements demand more. Ensure module declarations, reexports, requests, helpers, manifests, and trait forwarding agree on availability. Derive any required closure from the same represented uses.
5. Keep input scope, overrides, package metadata, and event formats explicit. The SDK's `in_package: v2.core` and similar annotations need deliberate family mappings; the current crate configuration rejects unknown packages. The current webhook extractor assumes a snapshot wrapper with a single `object` field; thin schemas do not satisfy that contract. Classify them before extracting payloads. Scope the v1 ApiVersion override and crate configuration deliberately for a v2-only input; missing required selectors inside an applicable scope remain errors. Preserve include and nullability information instead of converting include behavior into expandable relationships.

These changes build on useful existing boundaries: stable run-local component/operation IDs, distinct canonical items and request models, conservative local deduplication with origins, separate item layout/addressing, shared dependency traversal, and staged materialization. V2 should exercise those boundaries with additional facts and policies. If it requires a second renderer, duplicate type graph, or version checks throughout unrelated model code, the boundary is still wrong. The broader placement/feature work should follow the first generated slice rather than become a prerequisite framework rewrite.

**Staged experiment after this planning checkpoint.**

1. Establish the client compilation boundary and an explicit development input/scope. Keep the production pin and CLI unchanged. Acceptance: a minimal client or v2-only consumer has no v1 Shared/DTO source in its actual compilation inputs, while the legacy verification still has an identifiable baseline.
2. Generate the complete Event Destinations family with concrete types: list, create, retrieve, update, delete, enable, disable, ping, generic Event, deletion response, and the generic v2 error envelope. Include a standalone thin-notification parse example and verify that it does not activate resource DTO packages. Do not pull all detailed errors or webhook payloads into this slice by default.
3. Add v2 Accounts beside v1 Account and exercise an ID passed between the two endpoint families. Include representative customer configuration/payment-method ID fields and endpoint-specific `include` requests. Acceptance: distinct DTOs and correct public paths; no new v2-to-v1 DTO edge or cross-version deduplication. For useful compile comparisons include complete account-family request/model output rather than one handpicked tiny Account endpoint.
4. Change placement when a dependency or artifact-size finding gives a useful layout question to test. Compare alternatives using identical generated APIs, concrete representations, requests, serde options, toolchain, compiler profile, and benchmark collector. There is no requirement to implement all three candidates or settle published packaging during the first slice. Keep opaque v1 results separate and provenance attached.

Runtime checks should cover both Hyper and async-std/Surf (including blocking execution where supported): exact full URLs; authorization and required Stripe-Version; Stripe-Account and Stripe-Context behavior; JSON POST including an empty body; indexed GET query arrays; selected response types; metadata map entry deletion as JSON null; v2 error envelopes; stable idempotency keys across retries, including DELETE; and two-page pagination using the returned next-page URL with its filters and context intact. The pinned schema already makes update metadata values nullable, so that case needs serialization validation rather than a speculative new abstraction.

Use a separate v2 page/list type and paginator. The current v1 paginator strips `/v1` and uses object cursors; its list recognition expects `object: list`, whereas the pinned v2 list responses expose data and page URLs. Include-dependent response values can be represented by ordinary optional concrete fields initially, documented as potentially unrequested. They must not be interpreted as confirmed absent relations or automatically fetched on field access. Datetimes are RFC 3339 strings in the pinned v2 schema; preserve their wire shape before choosing a public timestamp helper. [API v2 behavior](https://docs.stripe.com/api-v2-overview), [include semantics](https://docs.stripe.com/api-includable-response-values)

Official SDK transport corroboration uses Stripe Python `v16.1.0`, commit `94756ffee7754e2fddc4bf5de4c3a407971128a5`, which targets the newer API revision `2026-10-28.endive`. It distinguishes JSON bodies and query encoding, sends Stripe-Context, generates keys for POST and v2 DELETE, follows page URLs, and keeps typed related-object fetching separate from the notification's stored identifiers. Its source supports the runtime plan, not a claim of schema equivalence with `v2494`: [requestor](https://github.com/stripe/stripe-python/blob/94756ffee7754e2fddc4bf5de4c3a407971128a5/stripe/_api_requestor.py), [paginator](https://github.com/stripe/stripe-python/blob/94756ffee7754e2fddc4bf5de4c3a407971128a5/stripe/v2/_list_object.py), [typed event helper](https://github.com/stripe/stripe-python/blob/94756ffee7754e2fddc4bf5de4c3a407971128a5/stripe/events/_v2_core_account_created_event.py).

For each useful layout comparison record canonical model modules/declarations, fields, variants, and SCCs; resolved feature/dependency graphs; and actual compiler sources from dep-info. Use the current `bench/compile` collector's measurement approach: one clean build per selected workload/profile, original and stripped executable bytes, text/debug section bytes, per-library `.rlib` and `.rmeta` sizes with enabled features, and dev incremental-cache bytes split between the consumer and Stripe libraries. Keep `.rlib` and `.rmeta` measurements separate because archives already contain metadata. Add LLVM line and copy counts for the consumer and the specific library units whose generated-code cost is under investigation. Consumer-root IR excludes separately compiled dependencies; the existing standalone Shared diagnostic also has a distinct scope. Neither is a whole-program count. Selecting v2 library units will need a narrow extension of the current Shared-specific diagnostic, not a new benchmark system.

Final executable size describes retained linked code; it does not expose all generated library/compiler work. Library artifacts, LLVM IR, and compiler source/dependency reports provide the other views. Match toolchain, target, profile settings, features, workload hashes, path remapping, and collector provenance across comparisons. Reuse a separately built collector against isolated generated workspaces, adding focused v2 workloads as needed. The collector is currently in the separate benchmark checkout, not this refactor baseline; `inputs.json` records the inspected reference. Do not import unrelated benchmark-branch changes into the experiment.

Workloads should include client only, Event Destinations only, Accounts only, Events plus Accounts, the same existing v1 consumer alone and with v2 added, thin notifications alone, and all supported v2 families. Introduce them as the corresponding slice becomes available. Use fresh consumer workspaces so dev dependencies or all-workspace features cannot inflate the minimal cases, and keep caches outside worktrees. Do not request repeated timing runs or use wall-time thresholds to select a layout. Artifact and IR differences are the primary quantitative evidence; structural graphs explain which dependency and placement decisions produced them.

The v2 experiment succeeds architecturally if ordinary concrete v2 families stay independent of v1 DTOs and unrelated v2 families, while runtime and codegen changes remain localized and placement stays easy to change. Matched artifact, IR, and compiler-input reports should establish whether a layout reduces generated library work or concentrates less of it in one compilation unit. They do not establish a measured wall-time speedup. An Event-only improvement combined with an unchanged v1 Shared bottleneck in mixed applications is a meaningful, bounded result, not evidence that v2 solved v1 globally.
